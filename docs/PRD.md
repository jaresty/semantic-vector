# Product Requirements Document: semantic-vector

- **Status:** Draft
- **Product:** `semantic-vector`
- **Initial implementation language:** Go
- **Repository:** `https://github.com/jaresty/semantic-vector`
- **Audience:** library maintainers, contract authors, test authors, independent reviewers

## 1. Product summary

`semantic-vector` is a testing library and associated technique for turning behavioral contracts into independently reviewable executable evidence.

Its central artifact is a **semantic vector**: a governed property paired with a valid semantic world and one controlled violating world, together with exact expected results, typed failures, observable effects, provenance, and an explicit evidence ceiling.

The library helps teams determine whether tests discriminate semantic behavior or merely exercise labels, sentinels, or implementation-shaped expectations.

## 2. Problem

Contract-heavy systems frequently use fixtures, golden files, property tests, mutation tests, and model-based tests independently. These approaches leave recurring gaps:

1. a fixture can encode an example without naming the property it establishes;
2. a golden test can compare bytes generated by the same implementation under test;
3. a mutation can change an input without proving that only one governed semantic property changed;
4. a test can observe the returned value while ignoring writes, accounting, ownership, or publication effects;
5. a test can fail unconditionally or accept a generic `not implemented` result without discriminating behavior;
6. a test suite can contain many named cases while exercising the same label-based path;
7. concurrency tests can use separate stores or uncontrolled schedules and therefore fail to test shared arbitration;
8. reviewers can see assertions without being able to reconstruct the source contract or oracle authority.

The product must make these deficiencies mechanically visible without claiming to establish the correctness or completeness of the underlying contract.

## 3. Goals

### G1. Executable semantic contrasts

Represent a valid world and controlled violating world as one reviewable vector whose guard must classify the two differently.

### G2. Exact expectations

Support exact canonical inputs, outputs, typed failures, and effects, including explicit zero effects.

### G3. Property provenance

Bind each vector to a stable property identity and human-readable source reference.

### G4. Independent oracles

Record how expected values were produced and whether the oracle is independent of the implementation under test.

### G5. Fixture self-validation

Reject malformed, nondiscriminating, ambiguous, incomplete, or duplicate vectors before they are used to assess production behavior.

### G6. Deterministic execution

Produce stable vector identities, ordering, reports, and concurrency schedules where deterministic scheduling is selected.

### G7. Incremental adoption

Permit projects to begin with result-only vectors and progressively add canonical bytes, effects, perturbations, concurrency, and completeness manifests without silently overstating evidence.

## 4. Non-goals

The product will not:

1. decide whether a product requirement is correct;
2. prove that a vector set is semantically complete;
3. generate authoritative expected results from production code;
4. infer feature identity, ownership, purpose, acceptance, or completeness;
5. replace fuzzing, property testing, race detection, mutation testing, or model checking;
6. prescribe a storage engine, serialization format, or concurrency architecture to systems under test;
7. automatically mutate arbitrary domain objects without an explicit mutator;
8. treat passing vectors as release or publication authority;
9. integrate with `lsp-trace` in the initial repository milestone;
10. provide production-ready execution in the initial API scaffold.

## 5. Target users

### Contract author

Defines governed properties, admissible worlds, evidence ceilings, and required observable effects.

### Vector author

Creates valid worlds, controlled perturbations, expected observations, and oracle provenance.

### Library maintainer

Provides generic validation, execution, reporting, deterministic scheduling, and format compatibility.

### Independent reviewer

Checks whether vectors faithfully represent the contract and whether expected values are independent.

### Adopting application team

Maps domain inputs, outputs, failures, effects, and concurrency operations onto the generic interfaces.

## 6. Terminology

- **Property:** A stable identity and statement describing one governed outcome or behavior.
- **World:** The complete typed input and environmental state supplied to the system under test.
- **Valid world:** A world expected to satisfy the governed property.
- **Perturbation:** An explicit transformation from a valid world to a controlled violating world.
- **Violating world:** A world expected to violate the governed property in a declared way.
- **Observation:** Returned output, typed failure, effects, accounting, or other accessible behavior.
- **Effects:** Observable state changes, including explicit zero effects.
- **Oracle:** The independently reviewable source of expected observations.
- **Contrast witness:** Evidence that one guard classifies the valid and violating worlds differently.
- **Evidence ceiling:** Claims the vector cannot establish, regardless of pass status.
- **Vector pack:** An immutable, versioned collection of vectors and a completeness manifest.
- **Schedule:** A declared ordering or synchronization plan for concurrent operations.

## 7. Design principles

### P1. Contrast before confidence

A guard is not discriminating unless it can produce both satisfying and violating observations.

### P2. Results and effects are coequal

A returned error does not establish refusal-before-effect. Expected effects must be explicit.

### P3. Zero is data

No writes, no candidates, and no publication are represented as zero values, not omitted fields.

### P4. Oracles disclose custody

Every expected value identifies its origin, method, revision, and independence classification.

### P5. Domain semantics remain outside the generic runner

The library executes declared vectors; it does not interpret application concepts such as checkpoint, candidate, or owner.

### P6. Evidence is bounded

Passing vectors establish conformance only for the represented worlds, observations, and schedule.

### P7. Canonical identities are content-derived

A vector identity is computed from versioned canonical content, never display labels or execution order.

### P8. Fail closed on ambiguity

Unknown versions, duplicate identities, incomplete expectations, invalid mutations, and unsupported schedules are rejected before system execution.

## 8. Product model

A semantic vector is conceptually:

```text
property
+ valid world
+ controlled perturbation
+ expected valid observation
+ expected violating observation
+ oracle provenance
+ evidence ceiling
```

The runner performs:

```text
validate vector
→ execute valid world
→ execute violating world
→ compare both observations
→ establish or reject contrast
→ report bounded result
```

## 9. Functional requirements

### FR1. Property descriptors

The library shall represent a stable property ID, statement, source reference, and optional version.

### FR2. Typed worlds

The Go API shall support generic typed valid and violating worlds.

### FR3. Explicit perturbations

Each paired vector shall declare a mutator and a machine-readable change set. The library shall reject an unchanged violating world.

### FR4. Exact expectations

A vector shall be able to specify expected output, typed failure, canonical bytes, and effects for both worlds.

### FR5. Explicit forbidden effects

Effect expectations shall distinguish omitted knowledge from an explicit expected zero.

### FR6. Vector validation

Validation shall detect at minimum:

- missing property identity;
- duplicate vector identity;
- absent oracle provenance;
- absent evidence ceiling;
- identical valid and violating canonical worlds;
- untyped expected failures;
- internally inconsistent canonical hashes or lengths;
- nondeterministic identity inputs;
- unsupported format versions.

### FR7. Contrast execution

The runner shall execute both worlds through the same adapter and report whether their classifications differ as declared.

### FR8. Observation adapters

Applications shall map domain-specific outputs, failures, and effects into comparable typed observations without requiring the generic package to understand the domain.

### FR9. Independent oracle metadata

The library shall represent oracle type, source, revision, producer, method, independence class, and review status.

### FR10. Completeness manifests

A vector pack shall optionally declare the complete property set expected for that pack. The library shall report missing, duplicate, and surplus property mappings without claiming semantic completeness.

### FR11. Canonical fixture transport

The library shall support strict versioned JSON transport for vector metadata and exact byte payload references. Unknown fields and noncanonical encodings shall be rejectable under strict mode.

### FR12. Immutable identities

Vector and pack identities shall be reproducible from canonical bytes using a versioned digest algorithm.

### FR13. Deterministic ordering

Reports shall order packs, properties, vectors, worlds, and findings deterministically.

### FR14. Concurrency vectors

The library shall support multiple operations against one explicitly shared system-under-test context.

### FR15. Controlled schedules

Concurrency vectors shall declare barriers, release points, owner identities, and allowed schedules. The initial implementation may support only deterministic schedules.

### FR16. Effect accounting

Concurrency observations shall support attempts, creates, compares-and-swaps, swaps, conflicts, waits, takeovers, owner losses, writes, and domain-defined counters.

### FR17. Failure-position vectors

A vector pack shall be able to represent failure before, during, and after named stages, each with exact expected accounting.

### FR18. Reporting

The runner shall produce a structured report and a human-readable rendering containing:

- vector identity;
- property identity;
- valid and violating verdicts;
- output/failure/effect mismatches;
- contrast status;
- oracle provenance;
- evidence ceiling;
- deterministic reproduction information.

### FR19. Replay

A report shall contain sufficient stable identifiers to rerun one vector without relying on display names.

### FR20. Library self-tests

The project shall test malformed vectors, nondiscriminating adapters, altered canonical bytes, duplicate identities, incomplete effects, and concurrency schedule errors.

## 10. Nonfunctional requirements

### NFR1. Determinism

Given the same vector pack, adapter, implementation revision, and declared schedule, canonical reports shall be byte-identical.

### NFR2. Generic type safety

The public Go API shall use generics where they prevent untyped `any`-based world, output, failure, or effect matching.

### NFR3. No hidden I/O

Core validation and comparison shall perform no network or filesystem access. Loaders may be provided as separate packages.

### NFR4. Bounded resources

Parsers and runners shall accept explicit limits for vector count, canonical bytes, payload bytes, operations, effects, schedule steps, and report bytes.

### NFR5. Fail-closed parsing

Malformed, unsupported, over-limit, duplicate, or noncanonical fixtures shall fail before adapter execution.

### NFR6. Race safety

Runner and report components advertised as concurrency-safe shall pass focused Go race testing.

### NFR7. Stable compatibility surface

Public formats and APIs shall use semantic versioning. Canonical-byte changes require a format-version change.

### NFR8. Inspectability

Every rejection and mismatch shall identify its vector, property, world, comparison surface, and typed reason.

### NFR9. Minimal dependencies

The core package should prefer the Go standard library. External dependencies require a documented capability benefit.

### NFR10. Portability

The core package shall support currently maintained Go releases on Linux, macOS, and Windows unless a capability is explicitly platform-qualified.

## 11. Narrow functional v1 and future Go API

The implemented v1 is a small, functional in-memory contrast kernel with explicit v0 identity/report compatibility encoders. It provides generic typed properties, oracle metadata, evidence ceilings, canonical worlds, expectations, perturbations, executable custody, vectors, adapters, runners, and reports. Callers provide deterministic trusted codecs and an explicit observation classifier. Execution validates codec-backed canonical bytes, completes the valid-world observation before decoding the violating execution value, compares output, failure, effects, and classification separately, and emits bounded reports.

The exact implemented boundary and intentional narrowing are maintained in [`SCOPE.md`](SCOPE.md). In particular, v1 uses verified whole-world before/after digests and does not claim generic field-path or semantic-dimension verification. The staged API validates and snapshots canonical data before adapter binding; it retains keyed trusted executable dependencies and therefore cannot freeze closure behavior, authenticate custody, establish concurrency safety, or prove that an author was independent of implementation behavior.

The broader product model in this draft remains future work. Fixture generators, fixture transport and public canonical schemas, completeness manifests, a general resource-limit framework, generic concurrency scheduling and CAS support, and integrations are not implemented by v1. Future API additions such as vector packs must not be inferred from the current package.

The API shall avoid embedding domain names such as checkpoint, candidate, or feature.

## 12. Vector format

A future `semantic-vector/v1` transport shall contain:

```json
{
  "schema": "semantic-vector/v1",
  "id": "sha256:...",
  "property": {
    "id": "...",
    "statement": "...",
    "source": "...",
    "version": "..."
  },
  "oracle": {
    "kind": "independent-model",
    "source": "...",
    "revision": "...",
    "producer": "...",
    "method": "...",
    "independence": "independent",
    "review": "reviewed"
  },
  "valid": {},
  "perturbation": {},
  "violating": {},
  "expectedValid": {},
  "expectedViolating": {},
  "evidenceCeiling": []
}
```

Large exact payloads may be stored as content-addressed files referenced by digest, length, media type, and canonicalization profile.

The final schema is not frozen by this PRD.

## 13. Oracle independence

The product shall classify oracle provenance at least as:

- **independent:** derived without production implementation logic;
- **diverse:** produced by a separately implemented algorithm sharing the contract;
- **reference:** sourced from an accepted external artifact;
- **implementation-derived:** generated by the implementation under test;
- **unknown:** independence not established.

Implementation-derived or unknown oracles may be executed but shall be visibly downgraded. They cannot establish independent conformance. Independence is a declared provenance claim, while independently reviewed status requires separate bounded evidence naming reviewer, scope, source, and revision. The default is `UNVERIFIED`; caller-authored strings never self-qualify.

A reviewer must be able to reconstruct which bytes were supplied by the oracle and which were observed from execution.

## 14. Runner behavior

Before executing the adapter, the runner shall eventually:

1. validate format and limits;
2. verify canonical identities;
3. validate property and oracle metadata;
4. construct the violating world through the declared perturbation;
5. verify that the declared change set matches the observed world difference;
6. reject unchanged or over-broad perturbations;
7. execute valid and violating worlds under the same adapter contract;
8. compare output, failure, and effects independently;
9. establish whether the contrast is discriminating;
10. emit a bounded report.

The runner shall never convert a test pass into product acceptance authority.

## 15. Mutation discipline

A perturbation shall name the fields or semantic dimensions it intends to change. A vector is invalid when it changes undeclared dimensions unless the vector explicitly models a compound violation.

The library shall distinguish:

- byte difference;
- structural difference;
- declared semantic difference.

The generic library can prove byte and declared structural differences. Domain adapters or independent reviewers remain responsible for semantic interpretation.

## 16. Concurrency support

Concurrency testing shall use one explicitly shared context. Separate stores or owners shall not qualify as shared arbitration evidence.

A concurrency vector shall define:

- operation identities;
- shared context identity;
- owner identities and epochs;
- synchronization barriers;
- release sequence;
- allowed outcomes;
- exact aggregate effects.

The runner shall report arrival order, release order, and completion order separately. None is semantic order unless the vector explicitly defines that relationship.

## 17. Reporting

### Human report

Optimized for review, showing one vector per section with concise mismatches and reproduction instructions.

### Machine report

Versioned canonical JSON suitable for CI retention and comparison.

### Required statuses

At minimum:

- `PASS`;
- `VALIDATION_FAILED`;
- `VALID_WORLD_MISMATCH`;
- `VIOLATING_WORLD_MISMATCH`;
- `NONDISCRIMINATING`;
- `ORACLE_UNQUALIFIED`;
- `UNSUPPORTED`;
- `INCOMPLETE`.

A status is a testing result, not semantic acceptance. Implemented reports separately expose expectation mismatch, execution failure, test-definition defect, and contrast/discrimination. Authoritative causal attribution remains `UNRESOLVED` in v1. Callers may attach a separate `DECLARED_UNVERIFIED` attribution claim, but strings do not establish review, verification, or responsibility.

## 18. Versioning and compatibility

The Go module shall use semantic versioning after its first public release.

Before `v1.0.0`, incompatible API changes are permitted but must be recorded in release notes.

Fixture formats shall carry independent schema versions. Readers may support multiple versions, but writers emit only one declared version.

Canonicalization profiles and digest algorithms are versioned components of identity.

## 19. Security and privacy

The library shall assume fixtures may contain sensitive source or customer data.

Requirements:

- no implicit network access;
- no telemetry by default;
- payload redaction hooks for reports;
- content-addressed payload verification;
- explicit size and work limits;
- safe handling of malformed JSON and deep nesting;
- no automatic execution of commands embedded in fixtures;
- reports must distinguish hidden payloads from absent evidence.

## 20. Adoption path for lsp-trace

Adoption is future work and requires separate authorization.

Proposed sequence:

1. stabilize `semantic-vector` terminology and API independently;
2. represent a small non-authoritative `lsp-trace` parser contract as a pilot pack;
3. compare the pilot against existing tests without replacing them;
4. independently review oracle custody and compatibility;
5. add an optional test-only dependency;
6. migrate one bounded fixture family;
7. evaluate clarity, runtime, and defect detection;
8. decide whether broader refactoring is justified.

The first pilot must not target the blocked ADR 0011→ADR 0007 composition chain. That chain may adopt the technique only after the library demonstrates value on a smaller qualified boundary.

## 22. Risks and mitigations

### R1. False authority

**Risk:** Passing vectors are treated as proof of product correctness.

**Mitigation:** Mandatory evidence ceilings and non-authoritative report language.

### R2. Oracle coupling

**Risk:** Expected values reproduce production logic.

**Mitigation:** Oracle provenance, independence classification, and reviewer-visible custody.

### R3. Fixture explosion

**Risk:** Exact vectors become expensive to author and maintain.

**Mitigation:** composable builders, content-addressed payloads, manifests, and bounded pilot adoption.

### R4. Shallow label compliance

**Risk:** Teams create many named vectors that exercise one sentinel path.

**Mitigation:** require typed worlds, controlled perturbations, and discriminating observations.

### R5. Over-generalized API

**Risk:** Generic abstractions become harder to use than domain tests.

**Mitigation:** keep the core small and publish domain mapping patterns separately.

### R6. Nondeterministic concurrency

**Risk:** timing-based schedules create flaky evidence.

**Mitigation:** deterministic barriers first; probabilistic stress testing remains complementary.

### R7. Canonicalization instability

**Risk:** harmless serializer changes invalidate identities.

**Mitigation:** version canonicalization profiles and retain compatibility readers.

## 23. Success metrics

During pilots, measure:

1. percentage of vectors with independently qualified oracles;
2. percentage with explicit effect expectations;
3. percentage whose perturbation produces a demonstrated contrast;
4. malformed or nondiscriminating vectors rejected before production execution;
5. defects detected that existing tests missed;
6. review time required to connect an assertion to its governing property;
7. fixture maintenance cost across compatible implementation changes;
8. deterministic rerun rate;
9. flaky-run rate;
10. adoption retention after the pilot.

These metrics evaluate utility; they do not establish semantic completeness.

## 24. Acceptance criteria

### PRD acceptance

- every section requested in the initial brief is present;
- the evidence ceiling is explicit;
- goals and non-goals are distinguishable;
- future `lsp-trace` adoption is bounded and non-authorized.

### Historical narrow v0 repository acceptance and current v1 transition

- repository is standalone and preserves its declared module path;
- `README.md`, `docs/PRD.md`, `docs/SCOPE.md`, and `go.mod` exist;
- the codec-backed generic API validates and executes valid and violating worlds through one adapter;
- valid observation capture completes before the violating execution value is decoded;
- historical v0 reports preserve evidence ceilings, oracle custody, typed findings, exact comparison surfaces, and explicit contrast classification;
- current v1 report identity adds observation-only classification and optional declared-unverified attribution claims without upgrading causal authority;
- tests cover malformed vectors, hostile cached-value codecs, nondiscriminating classifiers, unstable encodings, bounded reports, and failure-before-effects;
- no dependency or modification is introduced into `lsp-trace`.

### Future core acceptance

- malformed vectors fail before adapter execution;
- valid and violating worlds use the same adapter contract;
- reports compare outputs, failures, and effects separately;
- a nondiscriminating vector is rejected;
- canonical reruns are byte-stable;
- deterministic shared-context concurrency vectors reproduce exact accounting;
- public format and compatibility tests are independently reviewed.
